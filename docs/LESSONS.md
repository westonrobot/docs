# Lessons

Operational lessons for this repository, in Pattern / Correction / Context form. Consult during intake and after any error.

### Verify a layout change at the *binding* viewport, not the comfortable one

- **Pattern:** The landing page is designed to fit one viewport without scrolling, a constraint its own CSS and TSX comments state. Tightening the hero-to-cards gap raised two vh-scaled values (card media `20.5vh → 24vh`, `.main` top padding `2.2vh → 3.4vh`). Verified at 1920×1080, where it looked right, and committed. Both values also scale *down*, so at 1366×768 they cost exactly 36px and the page scrolled — the constraint broken by the change meant to improve it.
- **Correction:** A `vh`-scaled value changes every screen, not the one being looked at. When a layout rule names a viewport as its constraint, re-measure at that viewport before committing, and gate an increase behind `@media (min-height: …)` when it is only wanted where there is room. `document.body.scrollHeight <= window.innerHeight` is the check; run it at both ends of the supported range.
- **Context:** Docusaurus landing page, `src/pages/index.module.css`. The binding viewport here is 1366×768.

### A framing correction invalidates more than the sentence it lands on

- **Pattern:** The map lifecycle was corrected from two steps (draft → active) to three (push → publish → activate). The prose and tables were updated across nine places, but `tenant-management.md` ended up with the *corrected* diagram filed under the hierarchy section, where it did not belong, while the lifecycle section kept the *stale* two-step diagram — directly above the three-step table that contradicted it.
- **Correction:** After a framing correction, re-read the whole document rather than patching the places that matched a grep. Diagrams are especially prone to surviving a correction: they carry the claim in a form that text searches for the corrected wording do not match. Grep for the *old* shape (`draft.*activat` without `publish`) as well as the new one.
- **Context:** Markdown docs with mermaid diagrams; applies to any figure or table that restates a claim made in prose.

### Mermaid routes subgraph edges to the border, not the node

- **Pattern:** A `direction TB` subgraph inside a `flowchart LR` puts external edges on the subgraph's mid-height border. `TB -->|push| DRAFT` rendered as an arrow landing beside the middle node, so a three-stage pipeline read as "push → Published" — the exact misreading the diagram existed to prevent.
- **Correction:** Keep a subgraph's direction the same as the parent flow when edges cross the subgraph boundary. Check the rendered SVG, not the source: the source was correct and the picture was not.
- **Context:** `@docusaurus/theme-mermaid`, which renders client-side — `npm run build` cannot catch this, only looking at the page can.

### A customer-facing URL must carry an identity we own

- **Pattern:** 53 links across 11 pages died at the same instant because the M365 tenant was renamed `tangrobot` → `westonrobot` and `tangrobot.sharepoint.com` left public DNS. The links were not misconfigured and SharePoint did not fail; the URLs simply encoded a fact about the company inside a namespace Microsoft controls, so a change to that fact invalidated every one of them at once. The 30 `forms.office.com/r/…` links on the same pages still return `200`, because that hostname carries nothing about us. The first fix repeated the mistake: `adce7c6` moved four of our own documents to `drive.google.com/file/d/…?usp=drive_link`, which is the same shape — an opaque token in someone else's namespace.
- **Correction:** Anything handed to a customer resolves through a domain we own, with a readable path we chose, and the storage behind it stays a swappable implementation detail. When a third-party share link is the only option available today, treat it as a defect with a ticket rather than a fix. Before adopting a URL, ask which parts of it are facts that could change — a tenant name, an account, a product name, a vendor — because each one is a future outage. Verify the failure mode before diagnosing: `curl` returning `000` is DNS, and means something quite different from `403` or `404`.
- **Context:** External links from the docs site. Recorded in ADR 0001; issue #31 has the per-file inventory.

### "Reviewed" is not the same as "reviewed through a pull request"

- **Pattern:** Designing the file store, the requirement "publishing must be reviewed" was implemented as a git-tracked manifest with a PR approval. That made the docs repository the gate for every document: a technician with a PDF would have to open a pull request, the repo would accumulate a record of items it must not hold, and the review vehicle was chosen before the review was even specified. A second, related slip followed — the authoring flow sent the engineer to a console to upload before they could see the page work, which is backwards for anyone whose actual job is making the page right.
- **Correction:** Separate the property from the mechanism. Ask what the review must guarantee — attribution, an approval step, an audit trail — then pick the cheapest thing that provides it. Here an S3 object tag plus CloudTrail gives stronger attribution than a merge commit, at a smaller privilege, with no coupling to the repository. Where a workflow has an author in it, start where the author already is: local files, local build, then publish.
- **Context:** Infrastructure and workflow design. The tell was that `git` had to take on a role its content model contradicted — tracking an inventory of files it was deliberately not storing.

### A rule only one of two front doors can obey is not a rule

- **Pattern:** The file store's inbox was designed to key objects by content hash, so that `PutObject` alone could not destroy an earlier upload — overwrite safety by construction, with no deny rule to get right. It survived three rounds of review as prose. Writing the promote Lambda broke it in one line: **a technician dragging a file onto the S3 console cannot compute a digest.** The property was only ever available to the scripted route, and the design had two upload routes by deliberate choice.
- **Correction:** When a design serves more than one kind of user, check each rule against the *least* capable one before writing it down — a guarantee that holds for the scripted path and not the human one is not a guarantee, it is a hidden precondition. Here the fix was ordinary (versioning on the inbox bucket, digest computed at promotion) and gave the same property to both routes. More generally: prose review does not test a mechanism. This flaw was invisible across several careful readings and obvious after twenty lines of implementation, which is an argument for building the thin end of a design early rather than specifying it completely first.
- **Context:** Infrastructure design with mixed technical and non-technical users. Recorded in `docs/design/file-hosting.md` §3, which now carries the rejected version and why.

### Re-verify a global name after you change it, and don't sweep with `git grep`

- **Pattern:** Three bucket names were checked for availability and were free. Collapsing three buckets into one produced a new name, `wr-files`, which was never re-checked — and it returns `403`, meaning another AWS account holds it. S3 bucket names are globally unique, so the first `cloudformation deploy` would have failed on `BucketAlreadyExists`. It surfaced only because the runbook's pre-flight step was executed rather than merely written. The subsequent rename then missed a file: the sweep used `git grep -l`, which lists **tracked** files only, and the runbook had just been created and never added — so twenty occurrences in the one document an operator would actually follow were left pointing at a name that does not work.
- **Correction:** A uniqueness check is about a specific string, not about a naming scheme; re-run it whenever the string changes, and put it in the runbook's pre-flight so it runs again at deploy time. For repository-wide renames use `grep -r`, or `git status` first — `git grep` is blind to exactly the new files a rename is most likely to touch. Prefer names carrying the organisation (`westonrobot-files`) over short prefixes (`wr-`) in any global namespace, since a short prefix is what someone else has already taken.
- **Context:** AWS S3, and any global namespace — domains, package names, container registries. Found by running `infra/RUNBOOK.md` §0 against the account.

### A global-namespace prefix is noise in a local namespace

- **Pattern:** The S3 bucket needs `westonrobot-` in its name because bucket names are unique across every AWS account. That prefix was then carried into the IAM policy and group names — `westonrobot-files-publish`, `westonrobot-files-publishers` — where it does nothing: IAM names are account-local, and the account *is* Weston Robot. Worse, it pushed the meaningful part of the name to the end, and left the result sitting in an account that already had `s3-access-internal-file-exchange` and `FleetAppS3Access`, where "files" distinguishes nothing.
- **Correction:** Name each resource for the namespace it lives in. Ask what the name has to disambiguate *against*: for a bucket that is every bucket on earth, for an IAM policy it is the other policies in one account. Check the house style already present (`aws iam list-groups`, `list-policies --scope Local`) before inventing one — here it was PascalCase `<System><Scope><Verb>`, which `DocsDownloadPublish` follows and the original did not.
- **Context:** AWS naming, but the same split applies anywhere global and local namespaces meet — package names versus module names, domains versus hostnames, image tags versus container names.

### The convention to match is the neighbouring page's, not only the style guide's

- **Pattern:** A new Pocket2 scanner page was written against `docs/design/product-page-template.md` and passed every rule in it, then two inconsistencies surfaced on reading it beside its sibling. Battery life was published as "up to 120 minutes" — the vendor's own wording — where `manifold_pocket.md` two lines away in the same sidebar category says "about 2 hours"; and the three new guide pages were titled in sentence case (`Capturing a scan`) where all eleven existing pages under `tutorial/` use Title Case (`G1 Diagnostics Guide`). The template mandates sentence-case *headings*, which is a rule about `##`, and it says nothing about unit presentation at all.
- **Correction:** After following the template, read the new page against the page a reader will see next to it — the sibling in the same sidebar category, and the other pages in the same section. A style guide can only carry the rules someone thought to write down; the rest of the convention lives in the existing pages, and the reader who notices a mismatch is comparing two pages, not a page against a document. Where a vendor figure and a sibling page differ only in unit, convert to the sibling's unit and keep the vendor's qualifier: "up to 2 hours" preserves both. Where the convention turned out to be unwritten, write it down — this one became ADR 0002 D5 and a paragraph in the template.
- **Context:** Adding a page to an established section. Applies to any repeated convention a template does not enumerate: units, title case, row labels in specification tables, link-label phrasing.

### Prose written around a verified table is where an unverified claim gets in

- **Pattern:** Every figure in the Pocket2 specification table was copied from the vendor's published table and checked. The row *labels* were then tidied for consistency with the sibling page, and in that pass `| Battery | 4000 mAh handle battery, hot-swappable |` was written. The capacity is the vendor's; **"hot-swappable" is not in any source** — it was inferred from a manual paragraph about latch buttons and a photograph of a detachable battery. It would have shipped as a specification, on a page whose own lead-in says the figures are kept in full because they decide whether a capture works before travelling to site.
- **Correction:** Treat the sentence around a verified value as unverified until it is checked separately. The dangerous edit is not transcribing a number, which invites care — it is rewording, summarising or labelling near one, which feels like formatting. When a change touches a specification block, re-grep the finished text for adjectives and capability words (`hot-swappable`, `waterproof`, `field-replaceable`, `no ... slot`) and require a source for each; three of these were caught in one pass on that page, including an asserted absence — "there is no card slot" — which is a claim about a feature no source mentions either way.
- **Context:** Any page mixing vendor specifications with our own prose. `docs/design/product-page-template.md` §Rules already says never invent a specification; this is the mechanism by which it happens anyway.

### A fact that exists only inside a figure cannot be checked from extracted text

- **Pattern:** The Pocket2 port layout was published with the DATA port on the rear and Port C on the front. Both were wrong, and the way they became wrong is the interesting part: `pdftotext` gave a complete-looking manual, its §2.4/§2.6/§2.7 named `DATA` and `Port C` in prose, and neither sentence said which face. The gap was invisible because the extraction succeeded — the missing information was in a diagram, and a text dump of a page containing only a diagram looks identical to a text dump of a page containing nothing. `pdfimages -list -f 3 -l 3` on the published PDF later showed the truth: §2.1 *Physical Structure of Pocket 2* carries **only the 38 × 22 px header logo**, so Manifold do not publish a port diagram at all. Earlier in the same task the power-button location *was* checked this way — a page was rendered and read as an image — but only because a colleague's correction prompted it, not as routine practice.
- **Correction:** When a claim is about **where something physically is**, treat extracted text as insufficient by default. Render the page (`pdftoppm -png -f N -l N`) and read it, and run `pdfimages -list` over the section that should carry the drawing — an empty image list is itself a finding worth recording, because it means no vendor source exists and an operator with the unit is the only authority. More generally: a successful extraction is not evidence of a complete source. Ask what form the answer would take, and whether the tool used can carry that form at all.
- **Context:** Vendor PDFs as a source for hardware documentation. Also applies to spec values inside table images, pinouts in drawings, and any figure a caption refers to but does not describe.

### Do not link a manual at a pinned revision because "the reader should know which one they are reading"

- **Pattern:** The Manifold resource tables were built on a rule that sounded principled: software gets a download page because versions move, manuals get a direct URL because a reader benefits from knowing the revision. It was even written into an ADR as a deliberate split. The reasoning inverts on one question — *what happens when the vendor replaces the file?* The download page still resolves to the current manual; the pinned URL either 404s or, worse, keeps serving a superseded document with no indication that it has been superseded. The sibling Pocket page already demonstrated the failure mode with `?file=MindCloudGo_0.3.0.apk`, and the version in that URL is precisely why nobody noticed it had died.
- **Correction:** Customer-facing links go to the page the vendor maintains; the resource row says what the reader will find there. Keep the versioned URL as **internal provenance** — in the ADR and the working ledger — so it still records which revision the published claims were checked against. Those are two different jobs and the same URL should not be asked to do both. The tell for this class of mistake is a rule that treats two resources differently without the difference surviving the question "and then the vendor changes it".
- **Context:** External vendor resources on product pages. Extends `docs/LESSONS.md` "A customer-facing URL must carry an identity we own" — a version number is a fact about someone else's release schedule, and the same argument applies to it as to a tenant name.

### A vendor manual documents *a* build, not the one your colleagues run

- **Pattern:** The MindCloud Studio half of the Manifold guide was written carefully from the v1.6.10 user manual — dialogs named, defaults recorded, fields quoted. When the operator supplied screenshots of the same workflow, four of those claims were wrong: `Fast Load Mode`, `Robust Mode` and `Load Raw Point Cloud` **do not exist** in the build they run, the `Resolution` default was `0` rather than `2 mm`, the tab set differed (`PostProcessing`/`Display` against the manual's `Industry`/`Settings`), and the whole application was light-themed against the manual's dark. The build reported `v0.2.12`; the manual described v1.6.10. Nothing had gone stale — the two had never matched, and reading the manual more carefully would not have revealed it.
- **Correction:** Treat a vendor manual as evidence about *a* version, and say which one in the ledger. Where the reader will be looking at their own screen, write to **menu and field names** rather than defaults, checkbox inventories or positions, and carry an explicit note that the layout may differ — those survive a version gap; a list of the four checkboxes in a dialog does not. Ask for one screenshot from whoever actually runs the software *before* documenting a desktop workflow in detail; it is cheaper than the correction and it also reveals things the manual omits, like which tree node has to be selected before a tool becomes available.
- **Context:** Third-party desktop software documented from a PDF. Sharpest where a vendor ships per-platform builds at different versions — here a Linux AppImage against a Windows-authored manual.

### Verify the geometry after editing an image, not just the pixels you meant to change

- **Pattern:** Six approved screenshot redactions were applied with `convert -region … -blur … +region`. Each was re-cropped and read back at high zoom to confirm the right text was obscured, and each looked correct. Two of them had also been silently **resized** — 2436×1273 → 1946×1036 and 2559×1340 → 2472×1292 — because ImageMagick 6's `-region` alters the image's virtual canvas, and a write without `+repage` can commit that. An earlier dimension check had passed, but it ran *before* the files were rebuilt to adjust a blur position, and was not repeated afterwards. Publishing them would have put two silently downscaled screenshots on a page whose captions tell the reader to click and enlarge.
- **Correction:** After any image edit, assert the output dimensions against the input in the same command that writes the file — `identify -format "%wx%h"` before and after, compared, not eyeballed. Add `+repage` to every `-region` pipeline. And re-run *every* check after a rebuild, not just the one that prompted it: a verification that ran against the previous version of a file is not a verification of the current one.
- **Context:** ImageMagick 6 `-region`. The wider point applies to any pipeline where a later fix invalidates an earlier check — the earlier check does not fail, it simply stops being about the artefact you are shipping.

### Short prose is not automatically good prose

- **Pattern:** A prose sweep across the Manifold pages measured paragraph length, essay openings and stale phrases, and cut eleven paragraphs over ~60 words to zero. It reported the pages clean. A reader then opened the Pocket2 product page and found **"There is nothing to fit."** at the head of *Getting started* — four words, grammatical, factually true, and worthless: it narrated the emptiness of a template section instead of telling anyone anything. The same sentence had been sitting on the older Pocket page for months and was copied from there. A second, semantic sweep of the same pages then found roughly thirty more: link-strategy rationale aimed at customers, our own evidence limits ("checked on one unit only"), document-ownership language ("these guides own everything up to the `.pcd`"), the serial number explained twice on one page, and a superlative about the document itself ("matters more than anything else in this guide").
- **Correction:** Length and staleness checks are mechanical and worth keeping, but they cannot see reader value. Add a semantic pass that asks of each sentence: **what customer question does this answer?** — and if the honest answer is "none", or "only editorial history", or "only template completeness", cut it. Do the pass by reading the rendered page top to bottom as a customer, not by grepping: the failures are grammatically correct, so no pattern matches them. Then repeat it once after editing, because fixing one instance surfaces its twins elsewhere. The families worth naming are in `docs/design/product-page-template.md`.
- **Context:** Any documentation quality gate. It generalises: a check that measures a proxy (length) will pass content that fails the property you actually wanted (usefulness).

### A sentence that reads as authoritative is the one most worth checking against the source

- **Pattern:** The Pocket2 connection guide opened by telling the reader that *"the phone's automatic Wi-Fi switching is the commonest cause of a dropped session"*, and its troubleshooting table said *"in practice it is nearly always automatic network switching or a VPN"* — under a heading that introduced the table as **"the manufacturer's own answers, from the Pocket2 User Manual"**. The manual ranks nothing. Its §3.2 lists three settings to check when the app shows disconnected, in a flat bullet list, with no frequency claim anywhere; `grep -ci vpn` across all 48 files in the session's report archive returned **0**, so no operator ruling supplied it either. Two neighbouring sentences failed the same way: *"there is no label to hunt for on the unit"* (the manual is silent on whether the unit is labelled, and §2.1 is a blank half-page) and *"every symptom in When it will not connect below is some version of the phone deciding it knows better"* (three of the four rows are interference, a second phone holding the link, and a mid-scan drop). None of these was a misreading. Each was an invented ordering, negative or generalisation added to make sourced material read more confidently — and one of them was then attributed to the vendor.
- **Correction:** Superlatives, frequency claims, causal rankings and asserted absences are load-bearing claims, not connective tissue, and each needs a source the same way a spec value does. Three cheap tells, all greppable: **"commonest / usually / nearly always / in practice"** (a frequency claim — does the source count anything?), **"there is no … / never / every"** (an asserted negative or universal — silence in a source is not evidence of absence), and any such phrase inside a block introduced as the vendor's own words (attribution laundering, the worst case, because the reader has been told where it came from). Where the source gives a flat list, publish a flat list; a reader who works through three settings is no worse off than one who works through the "commonest" first.
- **Context:** Any page written from a vendor manual. It is the failure mode *after* the one recorded in "Short prose is not automatically good prose": those sentences answered no customer question, these answer one — confidently, and without a source.

### Alt text must describe the image you publish, not the one you were given

- **Pattern:** The MindCloud Go Home capture is published with the serial **value** blurred and the `S/N` label kept, to the operator's redaction ruling. Its `alt` still read *"showing POCKET2 Connected, a firmware version and serial number"* — written against the original screenshot and never revisited when the redaction was applied. A screen-reader user was told a serial number was on screen; the rendered image shows an empty grey box. The same drift produced a worse defect on the same page: a tip told the reader to match the Wi-Fi SSID suffix against the S/N on the Home page — a comparison the published captures make impossible, and one that, if true, published four characters of the very serial the redaction hid.
- **Correction:** Redaction is a content change, so re-read every `alt`, `caption` and body sentence that refers to the affected region afterwards — and treat a claim *about* a redacted value as part of the redaction's blast radius, not as separate prose. The check is to read the sentence while looking only at the published file: if it names something the reader cannot see, it is describing a file that is not being shipped.
- **Context:** Any screenshot published in redacted form. Extends "Verify the geometry after editing an image, not just the pixels you meant to change" — that one is about the file, this one is about everything that points at it.

### A detail pinned to an external instance is a maintenance obligation nobody scheduled

- **Pattern:** Three claims on the Manifold pages failed the same way, in three shapes that do not look related. A **pinned manual URL** (`?file=…_V1.3.4.pdf`) either 404s or silently serves a superseded revision. A **vendor-process claim** — *"give Manifold the phone model, they collect these"* — is true until Manifold changes intake, and then it is simply false. An **app label** — *"My ▸ Check for Updates"*, straight from manual §3.1 — became `Profile` one release later. None was wrong when written, none fails loudly, and only the first is reachable by any gate we run: `curl` catches a dead URL, but nothing checks a sentence about someone else's process or a menu name against the world. The app-label case is the sharp one, because **the contradiction was already published on the same page** — the Home screenshot's bottom navigation reads `Profile` while the prose beside it read `My`. Five CI gates passed over it. An operator reading the page found it.
- **Correction:** Ask of every externally-derived detail: *what does this bind us to, and how would we find out it had changed?* If the honest answer to the second is "a customer tells us", write the durable form instead — link the page the vendor maintains rather than the revision; publish the action the reader takes ("note the phone model for your support ticket") rather than our belief about what the vendor does with it. Where the detail genuinely must be pinned — a version baseline, a manual section number — it belongs in the ADR or the ledger as provenance, where going stale is harmless, not on a customer page. And when prose names a UI label, **read it against the screenshot published beside it**: that check costs nothing and would have caught `My` against `Profile` before a reader did.
- **Context:** The tagging/versioning family — this is the general statement of "A customer-facing URL must carry an identity we own" and "Do not link a manual at a pinned revision", which are the URL-shaped instances of it. Divergences found so far are recorded in ADR 0002 D6.

### Never publish a safety net you have not seen fire

- **Pattern:** Two sentences on the scanning guide told the reader the system would handle something for them. *"MindCloud Go will also warn you when you are moving too fast — if it does, slow down"*: the 33-page manual documents **no motion warning of any kind**, only a battery overtemperature warning. *"A controlled tilt covers it without any cost to tracking"*: nothing establishes that tilting is free. Both were written to make real guidance feel supported, and both are worse than the frequency claims recorded above, because a reader who is told they will be warned **stops watching for the thing themselves**. On a survey that fails silently and is discovered a site visit later.
- **Correction:** An asserted affordance — the app will warn, the system will catch it, this costs nothing — is a claim about behaviour, and behaviour needs a source you have seen: a manual line, a UI string in a screenshot, or an observation someone actually made with the equipment. Absence of a documented failure mode is not evidence of a safety net. When guidance genuinely has no backstop, say what the reader must do instead; that is the useful sentence anyway.
- **Context:** Any instruction where the consequence of being wrong is not immediately visible. Sharpest in capture, recording and long-running-job workflows, where the failure surfaces long after the moment it could have been fixed.

### A diagram is a claim, and it is the hardest kind to spot when it is wrong

- **Pattern:** A figure was drawn to illustrate the loop-closure section, working from the four bullets already on the page. One of those bullets — *"Finish near where you started, especially on a site survey. It is the highest-value loop you will walk"* — was our own over-reading of Manifold's *"plan a closed-loop path"*, and the drawing duly showed a route returning to its origin. The operator caught it in the picture, not the prose, even though the prose had said it for weeks and had already survived a dedicated sourcing sweep that morning. MindCloud Studio's manual settles it in one line: Loop Closure *"is typically employed when scanning paths **intersect or overlap**"* — crossing your own route is the requirement, the finishing point is not. Two further defects in the same figure were also only visible by looking: a dashed stub that read as noise, and a label clipped outside its frame.
- **Correction:** Source a diagram the way you source a sentence — from the manual or the ruling, never from the neighbouring prose, which is exactly how an unsourced claim gets laundered into a second, more confident form. Then **render it and look at it** at both themes and at 375 px before believing it; a build that succeeds tells you the SVG parsed, not that it is legible, unclipped, or true. Budget for iteration: every round here was driven by looking, and none of the problems was visible in the source. **And when the figure depicts a practice rather than a structure, ask the person who does it for a sketch before drawing anything.** Six drafts went by — circuits that left the floor uncovered, a retrace that overlapped without closing a loop — and a thirty-second hand drawing from the operator settled it in one pass. The drafts were not converging; they were sampling a space the operator could point at directly. A request for a sketch costs one message and is the cheapest input available.
- **Context:** Any authored figure. The asymmetry is what matters — a wrong sentence can be grepped, a wrong picture cannot, so the cost of getting a diagram wrong is paid over a much longer period.

### Check the repository's visibility, not the content's intended audience

- **Pattern:** Operational detail about the AWS account has been written into this repository twice. On 2026-09-02 it was named individuals alongside their credential state, and two access key identifiers; caught and redacted before release. On 2026-09-04 it was the account identifier, named individuals again, an unremediated security finding with the evidence needed to exploit it, the absence of audit logging, and a list of production host names; caught before any push. Both times the reasoning ran "this is internal engineering detail, and this is the engineering repo" — which is a judgement about the *content*, while the property that matters is a fact about the *repository*. `westonrobot/docs` is public: it serves `docs.westonrobot.com`. Neither occurrence was a slip of the keyboard; both were a filing decision made without checking where the drawer opens.
- **Correction:** Before writing operational detail anywhere, run `gh repo view --json visibility` and believe the answer. A repository whose job is publishing a website is published by definition, and a private-looking path inside it (`infra/`, `docs/design/`) changes nothing. Account identifiers, per-person credential state, security findings and infrastructure host names belong in the private infrastructure repository; this one keeps what a contributor needs in order to do their job, which for AWS is "ask to be added to the publishing group, then enrol MFA and issue your own key". The 2026-09-02 fix landed without a lesson being recorded, which is the whole reason there was a 2026-09-04 — when a redaction happens, write the rule down in the same change, or it is not a correction, only a cleanup.
- **Context:** This repository. The same check applies to any repo that builds a public artifact, and to issue trackers, wikis and CI logs, which are published by default more often than people expect.
